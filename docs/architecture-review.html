Shinro: architecture review
Architecture review · shinro

A router is a value, not a toolchain

Your four constraints are all one constraint: the Vite plugin has to stop being the product. Everything framework-shaped in the package today — the child process, the build coercion, the ambient module declarations — exists to prop up a bare specifier that a real file on disk resolves for free. prototype/tsdown already got this right. This was the argument for shipping it, plus the seven gaps I found in it — and it has since shipped: the prototype is now packages/shinro.

Ship the prototype. Delete the dev server, delete the build config, delete the ambient declarations. Then the adapter question you're worried about never arrives — because you never own an entry point, and a Hono instance is already the portable interface every runtime accepts.

The rest of this is: where the code contradicts your goals today (§1), the layering that fixes it (§2–3), the DX end to end (§4–5), the seven things the prototype misses (§6), and what to delete, in what order (§7–9).

§1 Your four "don'ts", scored against the code as it stands

Two of the four are already violated, and not subtly. Both violations trace to the same root: the only supported integration is a Vite plugin, so the plugin had to grow a dev story and a build story.

Your constraint Today Evidence
1. Not a framework holds No lifecycle hooks, no onStart/onShutdown, the app module is user-owned. §4.2 of the spec is unusually disciplined about this. Keep that section verbatim.
2. Don't own the server process broken src/server/dev.ts is a 133-line DevelopmentProcess that spawns a Node child, injects a generated runner that boots Vite in middleware mode, imports your entry through createServerModuleRunner, and restarts it on a debounce with SIGTERM. That is a framework dev server wearing a plugin's clothes. The spec even documents the SIGTERM contract (§31.2) — which is the tell: you only need a termination contract if you're the one terminating.
3. Keep type safety, no weird commands holds The RPC story is sound, the generated client is a real file anyone can import, and the CLI is one verb.
4. Don't own dev/build broken ShinroOptions.build carries outDir, fileName, minify, sourcemap, unbundle; the plugin's config() hook coerces rolldownOptions, preserveModules and ssr.external; and generateBundle fails the build on an unexpected extra chunk. Spec §21 spends a whole section on your bundler modes. None of that is routing.

Worth saying plainly: this isn't drift, it's gravity. A plugin is loaded by a toolchain, so the cheapest way to make anything happen is to reach for the toolchain's hooks. The fix is structural, not a matter of restraint — make the plugin optional, and the temptation is gone because the hook isn't there.

§2 The load-bearing decision you already made

.shinro/routes.ts is a real file, containing static relative imports and one chained Hono registration per route. That single choice is what makes every one of your goals reachable — and you made it already:

There is nothing in that file a bundler is needed for. No import.meta.glob, no virtual module, no require.context, no plugin transform. It is plain ESM that tsc can check, tsx/bun/node --experimental-strip-types can execute, and rolldown, esbuild, or webpack can bundle without knowing Shinro exists.

So ask what the Vite plugin is actually still for, and the honest answer is two things: calling generate() at the right moment, and resolveId-ing the bare specifier shinro/routes to that file. The first is a 20-line adapter. The second is the whole coupling — and it's self-inflicted, because shinro/routes isn't a package export, it's a fiction maintained by a resolver plus .shinro/shinro.d.ts to keep tsc from noticing.

Your prototype's answer — #shinro/routes via package.json imports — is correct, and the reasoning in the prototype README is the strongest argument in the repo. I re-derived the table and agree, including the conclusion that paths is the worst option available: it type-checks clean and then crashes under plain Node, because the thing that's wrong is a compiler option no runner reads.

One refinement

Keep the relative import working too, and document it. import { routes } from '../.shinro/routes.ts' needs zero package.json boilerplate and resolves in every runner and in tsc by construction. Make #shinro/routes the documented default because it survives moving app.ts, but don't let the generator or the validator treat the relative form as a mistake — it's the escape hatch for anyone whose package.json is generated or locked down.

§3 The layering, and the one invariant that protects it

Three layers, dependencies pointing strictly down. Nothing above the line may be imported by anything below it.

shinro/appRuntime · ships in your bundle
defineApp, defineHandler, defineMiddleware, ShinroEnv. Peer-depends on hono and nothing else. No node: imports, so it works on Workers, Deno, and in a browser test. This is the only Shinro module a running server loads.
▲ imported by app code only ▲
shinroCodegen core · dev-time, Node
generate(), watch(), loadConfig(), scan(). Owns everything that is genuinely yours:
  • route discovery, escaping, groups, catch-alls
  • conflict and namespace diagnostics
  • the normalized manifest
  • emitting routes.ts, client.ts, +types
Imports no bundler. Ever. That is the rule that keeps this honest.
▲ called by ▲
shinro/cli · /vite · /tsdownAdapters · optional, ~20 lines each
Each one answers exactly one question: when do I call generate()? CLI: now. tsdown: buildStart. Vite: configResolved plus a watcher. Anyone can write the fourth one in an afternoon — unbuild, rspack, a Turbo task, a Makefile.

The invariant to write into the spec

No adapter is ever load-bearing. If a project can only build, type-check, or run because an adapter ran, that's a bug in the core. Adapters exist to remove a manual step, never to enable a capability.

Make that testable, or it will rot in a month. Add one fixture app to the matrix that has no adapter at all — its only Shinro touchpoint is shinro generate in a package script, and it builds with plain tsdown (or plain tsc, see §6.1). If that fixture ever needs a plugin added to make CI pass, something crept back into the wrong layer.

§4 What the DX looks like

Install & wire, once

That's the entire surface: four imports lines, one extends, and a config file if you want to move the routes directory. No plugin required, no vite.config.ts required.

Authoring

Running it — four runtimes, one artifact, zero adapters

Node serve({ fetch: app.fetch }) nothing
Bun Bun.serve({ fetch: app.fetch }) nothing
Workers / Deno export default app nothing
Tests testClient(app) nothing

This is the direct answer to the adapter fear. A framework needs node/bun/cloudflare adapters because it owns the entry and must produce a listener, so it has to know what a listener is on each platform. You produce a Hono, which is already the portable interface — every runtime story is one line the user writes themselves. Cloudflare support is a docs page, not a code path. That stays true only as long as you don't own the build, which is the strongest argument for deleting build.*.

Invariant that keeps it true

Generated artifacts must stay runtime-neutral: no node: specifier, no process, no fs, no dynamic import() may ever appear in .shinro/routes.ts or client.ts. Today they don't. Assert it in a test so a future codegen convenience can't quietly cost you Workers.

§5 The dev loop: one process, and still no shinro dev

An earlier draft of this section built the loop on node --watch --watch-path=src --import shinro/generate and filed the platform question under "worth confirming before it's written down". Confirmed, and it kills that script as the default: Node's documentation still restricts --watch-path to macOS and Windows only (checked against current docs, July 2026). It hard-fails on Linux — which is Docker, devcontainers, WSL, Codespaces, and every CI smoke run. The NODE_OPTIONS + tsx watch --include fallback breaks on Windows cmd for the mirror-image reason. Neither survives as the one documented loop.

The fix is to stop needing --watch-path at all: move the directory watcher into the preload. Ship a second side-effecting subpath, shinro/watch — generate once, then start the in-process watcher from core/watch.ts. Plain --watch is graph watching, which every platform supports, and that turns out to be enough:

Three properties make it work, and each is load-bearing:

  1. --import completes before the entry is resolved. Generation finishes before anything resolves #shinro/routes. It has to be --import rather than an import inside a src/dev.ts: ESM loads a whole graph before evaluating any of it, so an in-graph import would resolve #shinro/routes before codegen ran — fine once .shinro exists, broken on a cold clone. That's the worst shape a bug can take, and it's the same ordering guarantee loader hooks depend on.
  2. The graph gap closes through the generated file. A brand-new route file is invisible to a graph watcher — nothing imports it yet. But the in-process watcher sees it, regenerates, and routes.ts changes — and routes.ts is in the graph via #shinro/routes, so --watch restarts. The new-file problem that justified --watch-path funnels itself through the one file the graph can already see. Edits to existing route files never need the watcher at all; they're in the graph on their own.
  3. The restart re-runs the preload, which regenerates and re-establishes the watcher — so anything that changed during the restart gap is reconciled on boot, and the tmp-then-rename writes in core/emit.ts mean no restart ever imports a half-written routes.ts. One restart per real change, no coordination between processes.
This makes an existing invariant load-bearing

Generation runs on every restart, and routes.ts is a file the graph watcher is watching — so an unconditional write triggers a restart, which regenerates, which writes — forever. I tested both directions: unconditional writes restart indefinitely, hash-then-skip settles at exactly one restart per real change. SPEC §25 already requires that unchanged files keep their modification time, filed among the niceties. It is the load-bearing invariant of the whole no-shinro dev design, and it deserves a test asserting mtime is untouched — not merely that the bytes match.

5.1 — Everything is generated into a temp directory first

The scan produces the complete generation in memory, and core/emit.ts then stages every file it means to change in a temp directory inside .shinro before promoting any of them by rename. That reads like a detail of writing files. It is actually the mechanism six separate guarantees in this design rest on, so it's worth listing what it buys:

  • No reader ever sees a half-written module. rename within one filesystem is atomic, so routes.ts goes from the old contents to the new contents with nothing in between. This is not theoretical here: the graph watcher fires on the write, so a plain writeFile races the restart it causes, and the losing side imports a truncated router. Staging inside .shinro rather than the OS temp directory is what keeps the rename atomic — across a mount point it degrades to a copy.
  • A failure leaves the previous generation byte for byte. Nothing is promoted until every staged file exists, so a route conflict found late, a full disk, or a SIGKILL mid-write all end with the tree that was already working. That is the difference between a dev loop that prints an error and one that crash-loops the runner on a typo — and it's what lets the preload treat a broken route tree as a diagnostic instead of a fatal error.
  • --check falls out of it for free. Because the generation is complete before anything touches disk, the check is the same code path with the write skipped: compare, report, exit. One implementation decides both "what should change" and "is this tree stale", so CI and the build cannot disagree about what stale means — which was the risk in §6.3.
  • The lock file disappears. Writing in place needed .shinro/.lock, a pid, a liveness probe, and stale-lock reclamation, all so two processes couldn't interleave halves of two generations. Staging plus deterministic output makes concurrency benign: a tsdown build beside a dev server stage separately and promote identical bytes. Roughly eighty lines of coordination deleted, and with them the failure mode where a killed process left a lock that made every later run wait out its timeout.
  • Unchanged files are never touched at all. The comparison happens before staging, so a no-op generation creates no temp directory, writes nothing, and moves no mtime — the steady state of the dev loop is genuinely inert rather than merely cheap. And because the temp files live under .shinro, they are invisible to the graph watcher and already covered by the one ignore rule the project has.
  • Pruning becomes provable rather than heuristic. The staged tree is the complete answer, so any generated file absent from it — the +types declaration of a deleted route, an older format's shinro.d.ts — is stale by construction. Deleting happens after promotion and only for files carrying the generated notice, so a mid-generation crash can't take a declaration with it.
What it actually costs
  • A Node floor. A .ts entry needs Node ≥23.6 for unflagged type stripping, or 22.12 with --experimental-strip-types.
  • Promotion is per file, not one directory swap. Deliberately: renaming a whole directory into place makes the generated tree briefly disappear, which editors observe as the project's types vanishing on every save. The consequence is that a failure between two renames can leave a new routes.ts beside an older manifest.json. The manifest is promoted last for exactly that reason — it describes the generation rather than being part of it, so it is the right thing to be behind.
  • A resident watcher in the dev process. A few fs.watch handles, dev-only and opt-in. It spawns nothing, restarts nothing, and installs no signal handlers, so the §3 invariants hold — but it is Shinro code living inside the user's server process, which the generate-only preload never was.
  • Linux recursive watching has a bug history. Recursive fs.watch landed on Linux in Node 20.13 and misbehaved for several releases after. core/watch.ts should maintain per-directory watchers there rather than trusting { recursive: true } — it owns the watcher either way, so the fallback is contained in one file.

Keep shinro/generate too — it's the right preload where a directory restart is preferable and --watch-path is available (macOS and Windows, skipping the resident watcher), and it's what graph-only runners pass through NODE_OPTIONS. Both are documented alternatives now, not the default. And keep shinro generate in prepare regardless: it's not about the dev loop any more — it's so a cold clone can run tsc, or open an editor, before anyone starts the server.

None of this argues for shinro dev. Node still owns the process: it restarts, it signals. The watcher writes files and the runner notices — that's the whole contract. A shinro dev that spawns the runner is dev.ts again under a friendlier name, and you'd be back to documenting SIGTERM semantics within a release.

§6 Seven gaps in the prototype

6.1 — The shipped tsconfig makes plain tsc impossible

You said users should be able to build with "normal tsc". They can't: tsconfig.base.json sets noEmit: true together with allowImportingTsExtensions, and the prototype's copy is identical. A project extending shinro/tsconfig can type-check and can be bundled, but tsc cannot emit — and the reason isn't obvious to the person hitting it, because the blocker is inherited from node_modules.

Cleanest shape given the trade-off: keep shinro/tsconfig as the check-only default (it's the common case, and it's what moduleResolution: "bundler" implies anyway), and ship a second export — shinro/tsconfig/emit — with rewriteRelativeImportExtensions, module: "nodenext", and no noEmit, for the tsc-emit path. Two files, both tiny, and the "build it however you want" claim becomes true. Prove it with a fixture that builds on plain tsc and runs the output.

6.2 — .shinro/rpc.ts is vestigial; delete the artifact

In the current package it's generated, declared in shinro.d.ts, exported from package.json, and asserted by three tests — while client.ts derives AppType from typeof app and never reads it. In the prototype it has decayed to exactly one line: export type { AppType } from "./client.ts".

That's the right thing to notice and the wrong place to stop. Because .route('/', routes()) merges the sub-router's schema into the parent, typeof app is the complete contract — which makes the spec's §23 "chained RPC application that re-registers every route" a second, independently-derived source of truth for the same thing. Two derivations of one contract is a divergence bug waiting for its first edge case. Drop rpc.ts, drop #shinro/rpc, and let client.ts be the only place AppType exists. If you want the specifier for back-compat, alias the package export at client.ts rather than emitting a file.

6.3 — generate --check for CI

Once no bundler is guaranteed to run, generate is the only moment Shinro can catch anything — route conflicts, namespace overlap, invalid method exports, all of §26. So it has to be the diagnostic surface, and CI has to be able to fail on it without writing files:

--check should also fail when artifacts on disk differ from what the route tree implies, so a stale committed .shinro/ or a forgotten regen is loud instead of mysterious. That's the moral equivalent of fmt --check, and it's the thing that makes committing .shinro/ a safe option rather than a trap.

The invariant --check quietly assumes

Byte-comparing memory against disk only works if codegen is deterministic: stable route ordering, no timestamps in headers, forward slashes in emitted paths regardless of platform. The header already gets this right — format 3, no date — but nothing enforces it, and the first nondeterministic emit turns --check into CI flake. Write it down as an invariant next to mtime-preservation and runtime-neutrality, with a test: two generates on the same tree, byte-identical, on every OS in the matrix.

The format number also earns its keep here: when the on-disk artifacts carry an older format than the installed package would emit, --check should say "generated by an older shinro — run shinro generate" instead of dumping a byte diff. That's the difference between a committed .shinro/ surviving a package upgrade and it becoming the confusing part of the changelog.

6.4 — basePath should be Hono's, not yours

The prototype app sets "basePath": "/v1" in config, and then has to hand-write the prefix on its manual route: .get('/v1/manual', …). That's the seam showing — one prefix mechanism that applies to file routes and not to the app, so the user maintains the other half by hand and nothing checks it.

Hono already has this: defineApp().basePath('/v1') prefixes manual routes and mounted sub-routers alike, and it's reflected in the schema, so the generated client's URLs stay correct with no work from you. Dropping basePath from the config removes a config key, a manifest field, a class of conflict diagnostics, and that whole seam. The one thing you lose is that Route['path'] in +types won't carry the prefix — which costs nothing real, since that string only feeds Hono's path generic for c.req.param typing.

6.5 — typeof app is the DX cliff nobody has hit yet

client.ts derives AppType from typeof app, and the "./client" export hands that to frontend workspaces — which means the consumer's tsc re-elaborates the entire server graph: every route, every zValidator schema, every link in the chained generic. Hono documents this slowdown on large chained apps and recommends compiling types rather than shipping the inference. At ten routes nobody notices. At eighty routes with validators it's the first complaint — and it lands on exactly the feature that is the reason most people are here.

The supported answer is probably tsc --declaration over client.ts: the emitted .d.ts flattens the chain so consumers elaborate nothing (a generate --dts flag can come later, once demand is proven). For v0.1 it's enough to document that path and add a fixture with ~100 generated routes and a type-check time budget in CI — so "the typed client scales" is a measured claim, not an assumed one.

6.6 — The first error a new contributor sees is Node's, not yours

validatePackageImports warns at generate time — but the failure a cold clone actually hits happens before generate runs: node src/server.ts throws ERR_PACKAGE_IMPORT_NOT_DEFINED, or a module-not-found pointing into a .shinro/ that doesn't exist, and nothing in either message says "run shinro generate". prepare covers install flows; it doesn't cover the person who cloned and ran a file directly.

Two cheap fixes. First, promote shinro init from a parenthetical to a specified command: idempotent, prints a diff of what it would change, merges into an existing imports block rather than refusing. It writes the four imports lines, the tsconfig extends, and the dev/prepare/check scripts — it is the whole onboarding, so it deserves the spec section the dev server used to have. Second, a docs page that lists the two or three pre-generate errors verbatim with their one-line fixes, so the search hit exists before the frustration does.

6.7 — Hono's typed overloads end at ten handlers, and inlining sails past them silently

routes.ts inlines every _middleware along the directory path plus the defineHandler tuple into one registration. There are three arity ceilings in that pipeline, and they fail very differently. defineMiddleware has none — it's a variadic tuple. defineHandler's hand-rolled ladder caps at ten elements and fails loud: "no overload matches", in the route file, where the author is. But Hono's HandlerInterface also ends its typed overloads at path + ten handlers, and past that lies a variadic fallback that infers one shared Input for everything — and that one fails silent.

Verified against hono 4.12.31 in the exact generated shape, pre-typed tuples spread into .get(): at ten args the client is fully typed. At eleven, zero diagnostics anywhere — not in the route file, not in routes.ts, not in app.ts — but that route's client input degrades to {} | undefined and .json() returns unknown. The validator's contribution to the contract just vanishes. Runtime is unaffected (fourteen handlers execute fine, in order), and c.req.valid() inside the route file stays typed, because that's established at the defineHandler site. It is specifically the generated client — the headline feature — that loses the contract. Worse, the count is a sum the user never sees in one place: three nested _middleware.ts files with three middleware each, plus defineHandler(validator, handler), is eleven — and no single file looks wrong.

The rejected alternative, chaining .use("/api/*", …) before the routes, breaks route-group scoping: two pathless groups share URL space, so path-pattern matching can't tell their middleware apart. Inlining is per-route precise, and composition keeps it that way.

Correction: composition is not free, so it is not the default

I claimed collapsing N middleware into one slot "loses nothing", on the grounds that defineMiddleware types every element as a plain MiddlewareHandler<Env, Path>. Building it disproved that. The tuple's const type parameter preserves each element's own inferred signature, so a middleware that short-circuits with c.json({ error }, 401) carries that typed response into its slot — and inlining puts the 401 in the route's client response union. every() returns a plain MiddlewareHandler, which erases it. The suite's own "directory middleware responses are part of the RPC response union" test is what caught it: composed, that union went to never.

So the shipped emitter inlines by default and composes per route, only where inlining would overflow. That keeps the higher-fidelity emit everywhere it fits, and where it doesn't, it trades one route's middleware responses for the validator contract of the whole chain — with a warning naming the route, because a silent trade is how this section's bug happened in the first place. The slot count is the sum of tuple lengths, not of files: three middleware in one _middleware.ts cost three slots.

Two guards that go with it

Composition shrinks the arity to 1 + the defineHandler tuple length — but a maximal ten-element tuple plus one middleware slot is eleven, over the cliff again. The scanner already parses every defineMiddleware and defineHandler call, so the arities are statically known: generate should hard-error when a route's emitted registration would exceed path + ten, naming the route and each contributing file's count — per 6.3, generate is the only moment this can be caught. And a type-level fixture (nine middleware + validator, expectTypeOf asserting the client's input and response stay concrete) pins both the emitter and Hono's ladder, so a hono upgrade that moves the cliff fails in CI instead of in someone's frontend.

One correction to the failure mode, from building it: how the over-limit case fails depends on the tuple's shape. With the validator first in a defineHandler tuple — the shape a composed route actually emits — an inlined eleventh argument does not go quiet. TypeScript rejects the variadic fallback outright ("no overload matches this call"), because the validator's H<Env, string, …> can't satisfy the fallback's H<ShinroEnv, "/path", {}, Response>. That is still an error the author never wrote and can't act on — it points at .shinro/routes.ts — so the generate-time diagnostic keeps its job. It just means the cliff is silent in some shapes and loudly misplaced in others, and both are reasons to catch it before emitting.

Both guards shipped: generate hard-errors when even composition cannot fit a route under path + ten, naming the route and each contributing file's count, and the type fixture lives in the suite. The one runtime cost is the import { every } from "hono/combine" the generated file gains — emitted only when some route composes. Still runtime-neutral, no node: specifier, so the §4 invariant holds.

§7 The cut list

Roughly 700 of the package's 3,900 lines, and they're the framework-shaped 700. Concretely:

cut src/server/dev.ts — DevelopmentProcess, the spawned child, the injected runner source, SHINRO_DEV_*, debounced restarts, SIGTERM semantics. With it goes spec §20 and §31.2.
cut ShinroOptions.build — outDir, fileName, minify, sourcemap, unbundle, and the config() coercion of rolldownOptions / preserveModules / ssr.external. With it, spec §21 entirely.
cut ShinroOptions.entry and the generateBundle chunk assertions — plus the two "unexpected extra chunk" / "external runtime assets" diagnostics in §26. Not routing.
cut .shinro/shinro.d.ts and resolveId for shinro/routes · shinro/client · shinro/rpc — package.json imports replaces both halves, and importing without a plugin becomes a real resolution error instead of a silently-empty router.
cut .shinro/rpc.ts and the duplicate RPC derivation in §23 (see 6.2).
change validateTypeScriptConfig — six conditions and a 30-line warning collapse to one question, now that ${configDir} lets the shipped base config carry rootDirs and include correctly.
change peerDependencies — vite and tsdown become optional peers; hono stays required. That line in package.json is the machine-readable version of this whole document.
change shinro typegen → shinro generate — it emits routes.ts, which is runtime code, not types. The core function is already generate(), so the verb should match it; typegen stays as a hidden alias. The old name tells people the router is a type artifact, which is the one thing you don't want them to believe.
keep scanner.ts (1,220 lines), ast.ts, codegen.ts, typegen.ts, factory/* — untouched. This is the actual product, and none of it ever needed a bundler.

§8 Where I'd push back on myself

JSON-only config is a small regression, and I'd still take it

No comments, no shared constants, no satisfies. The win — no jiti, no unconfig, a CLI that starts in milliseconds — is worth more, and the $schema you already ship covers most of what defineConfig autocomplete was doing. Give the adapters an inline options argument (shinro({ routes: 'src/api' })) for people who want config in code, with precedence: adapter options > shinro.config.json > package.json#shinro > defaults. Both idioms supported; neither requires a loader.

Should .shinro/ be committed?

Gitignored today, and the prepare script makes that work. But once the artifacts are plain files with no bundler in the loop, committing them has real appeal: a consumer of your ./client export doesn't need your dev toolchain, and tsc on a fresh clone just works. I'd keep gitignore as the default and make committing a supported, documented choice — which it only is once --check (6.3) exists to catch staleness.

The ShinroEnv augmentation is unusual, and it's still the right call

Application code augmenting a library's interface reads backwards, and it hard-limits you to one app per TypeScript program. But your §17.1 reasoning is airtight: inferring the env from typeof app when app.ts imports the generated router that is built on the env is a cycle. A declared env has no inference step to fail, which is worth more than the aesthetics. Keep it, keep the separate-tsconfig note for monorepos.

§9 Order I'd do it in

  1. Switch the specifier to #shinro/routes, delete shinro.d.ts and the three resolveId branches. Everything else depends on this, and it's the change that makes the package work without Vite at all.
  2. Extract generate() into the bundler-free core and make the CLI call it directly instead of loading vite.config.ts to find a plugin. The CLI stops being a wrapper around the plugin and becomes the primary interface.
  3. Delete dev.ts and build.*. Add the shinro/generate and shinro/watch preloads and have init write the one-line dev script. This is the commit where goals 2 and 4 actually become true.
  4. Add the no-adapter fixture and generate --check, with the determinism and mtime tests behind it. Switch the emitter to every() composition and add the arity diagnostic and type fixture from 6.7 in the same pass — they're all facets of one claim: what generate emits is exactly what the types promise. Now the layering is enforced by CI rather than by intent.
  5. Adapters: shinro/tsdown and shinro/vite, ~20 lines each, optional peers.

Every step is subtractive and behaviour-preserving for a correctly configured app, which means they can each land green, and none of them touches the authoring surface. Nothing in this document asks you to change how a route file is written.
